당근마켓 커머스팀 기술면접 예상 Q&A

01 Dynamic Import 선택 기준
Q
팝가 성능 개선에서 Dynamic Import를 선택한 기준이 뭔가요?
A
초기 렌더링에 필요 없는 모달 3개가 전역 번들에 포함되어 있었어요. 어차피 사용자 인터랙션이 있어야 열리는 UI라 SSR도 필요 없었고, ssr: false로 클라이언트 번들에서도 lazy 처리했습니다.
꼬리 — ssr: false를 안 하면 어떻게 되나요?
서버에서 렌더링 → 클라이언트에서 hydration 비용이 추가로 발생해요. 모달처럼 초기에 보일 필요 없는 컴포넌트는 hydration 자체가 낭비예요.
02 heic2any Script lazy 전환
Q
heic2any를 dynamic import 했더니 first load가 오히려 늘었다고 했는데, 왜 그랬을 것 같나요?
A
bundle analyzer로 확인하니 해당 라이브러리가 청크 분리 시 다른 모듈과 공유 청크로 묶히는 구조였어요. dynamic import로 분리해도 공유 청크 자체가 초기에 로딩되니까 first load는 오히려 늘었고, Script lazy 태그로 완전히 분리해서 해결했습니다.
꼬리 — Webpack 공유 청크는 왜 생기나요?
여러 모듈에서 공통으로 참조하는 라이브러리를 중복 포함하지 않으려고 Webpack이 자동으로 공유 청크를 만들어요. SplitChunksPlugin이 담당해요.
03 LCP 단계별 분석
Q
LCP를 TTFB / 리소스 로딩 지연 / 엘리먼트 렌더 지연 세 단계로 나눠서 분석했는데, 각각이 뭘 의미하나요?
A
TTFB는 브라우저가 요청을 보낸 뒤 서버 첫 바이트를 받기까지의 시간이고, 리소스 로딩 지연은 TTFB 이후 실제 리소스 fetch가 시작되기까지의 지연, 엘리먼트 렌더 지연은 리소스를 받은 뒤 DOM에 그려지기까지의 시간이에요. 팝가에서는 TTFB가 41.6%로 가장 큰 병목이었고, LCP 요소가 캐러셀 썸네일이어서 이미지 최적화로 접근했어요.
꼬리 — Lighthouse 점수는 괜찮은데 사용자 체감이 나쁠 수 있나요?
네. LCP는 첫 렌더 1회, INP는 대표 인터랙션 1회만 측정해요. 무한 스크롤 중 JS가 메인 스레드를 지속 점유하는 문제는 Core Web Vitals 범위 밖이에요. Performance 탭 CPU 4× 시뮬레이션으로 별도 확인했어요.
04 PostMessage vs SSE
Q
실시간 주문 수신에 SSE 대신 PostMessage를 선택한 이유가 뭔가요?
A
주문이 점심/저녁 피크타임에만 몰려요. SSE는 persistent connection이라 피크타임 외에도 서버 연결을 유지해야 해서 비용 낭비였고, 백엔드 구현 부담도 있었어요. 대신 Firebase messaging으로 네이티브가 주문을 수신하고, WebView로 PostMessage를 전달하는 구조를 선택했습니다.
꼬리 — WebView가 백그라운드 상태일 때는 어떻게 처리했나요?
Firebase push notification은 앱이 백그라운드여도 수신돼요. 사용자가 알림을 탭하면 앱을 foreground로 올리고, 그때 WebView로 PostMessage를 전달하는 흐름이에요.
05 WebView 환경 이해
Q
React Native WebView에서 작업하면서 일반 웹과 다르게 고려한 점이 있나요?
A
결제 앱 연동 시 앱 스킴 처리가 달라요. 일반 브라우저에서는 universal link가 동작하지만, WebView에서는 onShouldStartLoadWithRequest로 직접 가로채서 네이티브에서 열어줘야 해요. 그 외에도 키보드 인셋 처리, 네이티브 뒤로가기 버튼과 웹 히스토리 스택 충돌 등을 처리했어요.
꼬리 — 당근 앱 내 WebView에서 결제 연동을 구현한다면 뭘 먼저 확인하겠어요?
결제 PG사가 WebView 환경을 지원하는지, 앱 스킴 처리 방식, Android/iOS 정책 차이(특히 iOS Universal Link 제한) 순으로 확인할 것 같아요.
06 사전예약 서버 분리
Q
사전예약에서 프로젝트/서버를 분리한 이유가 뭔가요?
A
오픈 시점에 트래픽 스파이크가 예상되는데, 메인 서비스와 같은 서버면 스파이크가 메인에 영향을 줘요. 분리하면 격리가 되고, rewrite로 연결해서 사용자한테는 seamless하게 보이게 했어요.
꼬리 — Rate limiting이나 queue 방식과 비교했을 때 왜 서버 분리를 선택했나요?
Rate limiting은 과부하를 막지만 사용자 경험이 나빠지고, queue는 백엔드 구현 부담이 커요. 서버 분리는 메인 서비스에 영향을 완전히 차단하면서 프론트엔드 레벨에서 결정할 수 있는 방법이었어요.
07 전환율 측정
Q
쏠북 홈 개편 후 전환율이 40%→60%로 늘었다고 했는데, 어떻게 측정했나요?
A
Mixpanel로 구매 퍼널을 구축해서 홈 진입 → 상품 상세 → 구매 완료 단계별 이탈률을 추적했어요. 개편 전후 같은 기간을 비교했습니다.
꼬리 — 시즌이나 프로모션 같은 외부 변수는 어떻게 통제했나요?
완벽하게 통제하진 못했어요. 다만 직전 동일 기간과 비교하고, 특별한 프로모션이 없던 기간을 골라서 비교했어요. 엄밀한 A/B 테스트는 아니었습니다.
08 TanStack Query 도입
Q
쏠북에서 TanStack Query를 도입한 이유가 뭔가요?
A
이전에는 서버에서 받은 데이터를 전역 상태(Redux)에 저장했는데, 데이터 신선도 관리가 어렵고 불필요한 리렌더가 많았어요. TanStack Query로 서버 상태와 클라이언트 상태를 분리하고, staleTime/cacheTime으로 캐싱 전략을 명확하게 가져갔어요.
꼬리 — 캐시 무효화는 어떻게 관리했나요?
구매/결제 같은 mutation 후에는 invalidateQueries로 관련 쿼리를 즉시 무효화했어요. 목록 페이지는 staleTime을 짧게, 자주 변하지 않는 카테고리 데이터는 길게 설정했어요.
09 A/B 테스트 설계
Q
팝가에서 A/B 테스트를 진행했다고 했는데, 실험 설계를 어떻게 했나요?
A
플래닝 기능 오픈 후 지표를 보니 첫 퍼널에서 80% 이탈이 확인됐어요. "첫 화면 정보가 너무 많아서 이탈한다"는 가설을 세우고, 퍼널을 단순화한 버전을 Firebase A/B Testing으로 50:50 분배해서 테스트했어요.
꼬리 — 결과가 통계적으로 유의하지 않을 때는 어떻게 판단했나요?
Firebase가 통계적 유의성을 퍼센트로 보여주는데, 유의하지 않으면 더 오래 실험을 돌리거나 가설 자체를 재검토했어요. 샘플이 너무 적으면 결론 내기보단 실험을 연장했어요.
10 디자인 시스템 API 설계
Q
디자인 시스템을 3개 스쿼드가 쓴다고 했는데, 컴포넌트 API를 어떻게 설계했나요?
A
각 스쿼드 FE랑 미팅해서 공통 요구사항을 수집했어요. 스쿼드마다 쓰는 방식이 달라서 최소 공통 Props를 정의하고, 스쿼드별 커스터마이징은 children이나 slot 패턴으로 열어뒀어요.
꼬리 — Breaking change가 생기면 어떻게 관리했나요?
npm 배포라서 semver를 따랐어요. major 변경은 미리 각 스쿼드에 공지하고 마이그레이션 가이드를 함께 줬어요. 급하면 deprecation warning 먼저 추가하고 유예 기간을 뒀어요.
11 WYSIWYG 서버사이드 PDF
Q
WYSIWYG 에디터에서 Chromium 기반 서버사이드 HTML-to-PDF를 선택한 이유가 뭔가요?
A
클라이언트에서 PDF를 생성하면 폰트, 페이지 나눔, 수식 렌더링이 브라우저마다 달라져요. 서버에서 Chromium으로 렌더링하면 "에디터에서 보이는 것 = 출력물"이 보장되고, 4주라는 제약 내에서 가장 빠르게 스타일 한계를 극복할 수 있었어요.
꼬리 — 서버사이드 Chromium의 단점은 없나요?
서버 리소스를 많이 써요. 동시 요청이 많으면 병목이 생겨서, POC 단계라 큐 처리는 고려하지 않았지만 실서비스라면 job queue가 필요했을 거예요.
12 GTM 자동화 파이프라인
Q
Google Apps Script로 GTM 이벤트 자동 배포 파이프라인을 만들었다고 했는데, 어떤 문제를 해결한 건가요?
A
dev/prd 배포할 때마다 GTM 이벤트를 수동으로 퍼블리시해야 해서 휴먼 에러가 자주 났어요. dev 이벤트가 prd에 올라가거나 반대로 prd 변경이 누락되는 식으로요. Apps Script로 배포 시점에 자동으로 환경에 맞는 GTM 컨테이너를 퍼블리시하게 만들어서 휴먼 에러를 없앴어요.
꼬리 — 자동화하면서 잘못 배포될 위험은 없었나요?
dev/prd 컨테이너 ID를 환경 변수로 분리해서 교차 배포가 불가능하게 했고, 배포 전 슬랙 알림으로 팀원이 확인할 수 있게 했어요.
